# 비교 실험 기본기

이 문서는 Scenario A의 `ScenarioA_GenericHeavy_002`와 `ScenarioA_IrisHeavy_002`를 정리하면서 확인한 교훈을 바탕으로, 성능 비교 실험에서 결론을 내릴 때 특히 중요한 기준을 정리한다.

핵심은 단순하다.

> 비교 실험은 "무엇이 더 좋아 보인다"를 말하는 일이 아니라, "같은 조건에서 하나의 차이만 바꿨을 때 어떤 값이 어떻게 달라졌는지"를 증명하는 일이다.

## 1. 이번 일에서 가장 중요했던 부분

이번 측정에서 중요한 지점은 Iris가 켜졌는지보다, 비교가 성립하는 조건을 먼저 검증했다는 점이다.

처음 `ScenarioA_GenericHeavy_001`과 `ScenarioA_IrisHeavy_001`은 이름만 보면 heavy run처럼 보였다. 하지만 `run.json`을 확인하니 detail actor가 120개가 아니라 12개였고, `MetricsWindowElapsedSeconds` 컬럼도 없는 오래된 바이너리 산출물이었다. 따라서 이 run은 "실행됐다"는 사실과 별개로 heavy 비교에는 사용할 수 없었다.

이 판단이 중요하다. 실험에서 가장 위험한 실수는 결과 수치를 예쁘게 정리하는 것이 아니라, 비교하면 안 되는 데이터를 비교하는 것이다.

이번 작업에서 결론을 낼 수 있었던 이유는 다음 조건을 확인했기 때문이다.

- Generic과 Iris run이 같은 seed를 사용했다.
- 두 run 모두 detail actor 120개 조건이었다.
- 두 run 모두 run duration 95초, metrics start delay 35초, metrics duration 60초 조건이었다.
- client snapshot이 있어 각 role이 실제로 몇 개의 actor를 받았는지 확인했다.
- server network metrics에 같은 의미의 컬럼이 있었다.
- role 식별이 끝난 뒤, connection count가 3인 구간만 집계했다.
- 순간값 한 줄이 아니라 60초 window의 평균과 `OutTotalBytes` 증가량을 함께 봤다.

이 조건을 만족했기 때문에 `ScenarioA_IrisHeavy_002`에서 FieldAgent와 Spectator의 bandwidth 감소를 1차 결론으로 적을 수 있었다. 이후 `ScenarioA_20260601_201201`/`ScenarioA_20260601_201615`, `ScenarioA_20260601_203950`/`ScenarioA_20260601_204211` 반복 측정에서도 같은 heavy 조건과 같은 actor count 패턴이 재현되어, 3회 평균 기준으로 FieldAgent -24.7%, Spectator -31.8%, NetDriver delta -21.7% 감소를 기록했다.

## 2. 비교 실험에서 먼저 물어야 할 질문

결과를 보기 전에 아래 질문부터 확인한다.

1. 무엇을 비교하는가?

예: Generic replication과 Iris role-based filtering.

이 단계에서 비교 대상의 이름만 보면 안 된다. 실제 실행 조건으로 확인해야 한다. `mode`, `roleFiltering`, command line override, ini 값, 빌드된 바이너리 timestamp가 서로 맞는지 확인한다.

2. 무엇을 같게 유지하는가?

예: map, seed, actor count, role 구성, run duration, metrics window, client count.

실험의 신뢰도는 "무엇을 바꿨는가"보다 "무엇을 안 바꿨는가"에서 나온다. 비교 대상 외의 조건이 달라지면, 수치 차이가 어디서 온 것인지 설명하기 어려워진다.

3. 무엇 하나만 바꾸는가?

이번 비교에서는 가능한 한 `-UseIrisReplication`과 role filtering 상태만 차이로 둔다.

물론 현실에서는 Generic과 Iris 경로 자체가 내부적으로 다르고 완벽히 한 변수만 바꾸기 어렵다. 그래서 문서에는 "완전히 같은 시스템에서 한 줄만 바꿨다"가 아니라, "동일한 scenario 조건에서 replication mode와 filtering policy를 바꾼 비교"라고 정확히 써야 한다.

4. 측정값은 무엇을 의미하는가?

`OutBytesPerSecond`는 순간 또는 구간별 rate 값이다. 한 줄만 보고 결론을 내리면 흔들린다. `OutTotalBytes`는 누적값이므로 같은 window 안에서 마지막 값과 첫 값을 빼야 의미가 생긴다.

측정값은 이름을 외우는 것이 아니라, "이 값이 누적값인가, 평균인가, 순간값인가, 어느 범위의 값인가"를 먼저 해석해야 한다.

5. 결론을 낼 만큼 데이터가 충분한가?

한 번의 run은 방향을 보여준다. 반복 run은 신뢰도를 만든다.

이번 문서에서는 `_002` 결과를 유효한 heavy 비교로 기록한 뒤, 2026-06-01 반복 측정으로 같은 방향이 두 번 더 나오는지 확인했다. Scenario A의 actor filtering/bandwidth 비교는 3쌍 측정으로 마감하고, 더 깊은 원인 분리는 Unreal Insights, CSV, NetTrace 같은 profiling 산출물 수집으로 넘긴다. 한 번의 결과를 성급하게 법칙처럼 말하지 않는 것이 실험의 기본이다.

## 3. 유효하지 않은 데이터도 중요한 결과다

`ScenarioA_GenericHeavy_001`과 `ScenarioA_IrisHeavy_001`은 실패가 아니라 유효성 검사의 좋은 사례다.

실험에서는 무효 데이터를 버리기만 하면 안 된다. 왜 무효인지 남겨야 한다.

- RunId는 heavy였지만 실제 `detailActorTotal`은 12였다.
- 오래된 Server/Client 바이너리가 실행됐다.
- client snapshot CSV가 없었다.
- metrics CSV schema가 최신 비교 기준과 달랐다.

이렇게 남기면 나중에 같은 실수를 반복하지 않는다. 포트폴리오 관점에서도 "좋은 결과만 골랐다"가 아니라 "유효하지 않은 측정을 판정하고 제외할 수 있다"는 역량이 드러난다.

## 4. 결론은 세 단계로 써야 한다

실험 결론은 바로 "빨라졌다"로 쓰지 않는다. 세 단계로 나누면 안전하다.

1. 관찰

예: Iris heavy에서 FieldAgent의 `DetailActorTotal`은 120에서 40으로 줄었고, `AvgOutBytesPerSecond`는 2307.00에서 1740.18로 줄었다.

2. 해석

예: role-based filtering으로 FieldAgent가 자기 zone detail actor만 수신했고, 그 결과 outgoing bandwidth도 감소한 것으로 보인다.

3. 한계

예: 3회 반복에서도 같은 방향이 나왔지만 Commander도 같은 actor count를 받았는데 bandwidth가 줄었으므로 Generic/Iris 경로 차이나 packet/bunch 구성 차이는 별도 profiling으로 추가 확인해야 한다.

이 구조가 중요하다. 관찰, 해석, 한계를 분리하면 과장하지 않으면서도 자신 있게 결론을 낼 수 있다.

## 5. 실험 기본 지식에 익숙해지는 방법

실험 지식은 책으로 한 번 읽는다고 익숙해지지 않는다. 매번 같은 루틴으로 데이터를 다루면서 몸에 붙여야 한다.

### 5.1. RunId마다 작은 검증표를 만든다

새 run을 만들 때마다 먼저 아래 표를 채운다.

| 항목 | 확인값 |
|------|--------|
| RunId |  |
| 실행 명령 |  |
| 빌드/바이너리 기준 |  |
| Map |  |
| Mode |  |
| RoleFiltering |  |
| Seed |  |
| DetailActorTotal |  |
| RunDuration |  |
| MetricsStartDelay |  |
| MetricsDuration |  |
| Client snapshot 존재 |  |
| Server metrics 존재 |  |
| 비교 가능 판정 |  |

이 표를 먼저 채우면, 비교하면 안 되는 데이터를 초기에 걸러낼 수 있다.

### 5.2. "원본, 집계, 결론"을 분리한다

실험 데이터는 세 층으로 나눈다.

- 원본: `run.json`, `client_snapshots.csv`, `server_network_metrics.csv`
- 집계: 평균, delta, sample count, window start/end
- 결론: actor count 감소, bandwidth 감소, 추가 확인 필요

원본과 결론이 섞이면 나중에 검증이 어렵다. 결론을 바꾸더라도 원본은 그대로 남아 있어야 한다.

### 5.3. 비교 기준을 문장으로 먼저 쓴다

표를 만들기 전에 비교 기준을 문장으로 쓴다.

예:

```text
ScenarioA_GenericHeavy_002와 ScenarioA_IrisHeavy_002는 같은 seed, 같은 actor count, 같은 60초 metrics window를 사용한다.
집계 대상은 Scope=Connection, ConnectionCount=3, Role이 Unknown/Unassigned가 아닌 row로 제한한다.
```

이 문장을 먼저 쓰면, 나중에 표를 볼 때 "왜 이 숫자를 썼는지"가 남는다.

### 5.4. 반례를 일부러 찾는다

좋은 실험자는 원하는 결론을 증명하려고만 하지 않는다. 자기 결론을 깨뜨릴 수 있는 질문을 먼저 던진다.

- 같은 actor count를 받은 Commander도 왜 bandwidth가 줄었는가?
- 첫 35초를 제외했는데도 초기 replication 영향이 남았는가?
- Generic과 Iris의 packet/bunch 구성 차이가 actor filtering 효과와 섞였는가?
- client snapshot 시점이 metrics window와 완전히 같은가?
- 한 번 더 실행해도 같은 방향이 나오는가?

이 질문들은 결론을 약하게 만드는 것이 아니라, 결론을 더 튼튼하게 만든다.

### 5.5. 반복 가능한 명령으로 남긴다

실험은 "그때 어떻게 했더라"가 되면 안 된다. 실행 명령, RunId, 산출물 위치를 문서에 남긴다.

```bat
Tools\RunLocalBinariesMultiplay.bat --no-iris --run-id ScenarioA_GenericHeavy_002
Tools\RunLocalBinariesMultiplay.bat --iris --run-id ScenarioA_IrisHeavy_002
```

명령이 남아 있으면 같은 조건으로 다시 실행할 수 있고, 다른 사람이 검증할 수 있다.

## 6. 성능 실험에서 자주 하는 실수

| 실수 | 왜 위험한가 | 이번 사례의 대응 |
|------|-------------|------------------|
| RunId 이름만 믿는다 | 이름과 실제 조건이 다를 수 있다 | `run.json`으로 detail actor 수와 duration 확인 |
| 한 줄의 순간값으로 결론을 낸다 | 네트워크 지표는 흔들림이 크다 | 60초 window 평균과 delta 사용 |
| client 결과를 안 본다 | 서버가 보냈다고 클라이언트가 기대대로 받았다고 볼 수 없다 | `client_snapshots.csv`로 role별 actor count 확인 |
| 오래된 바이너리 여부를 놓친다 | 코드 변경이 반영되지 않은 결과일 수 있다 | `_001` heavy run을 무효 처리 |
| 실패한 run을 기록하지 않는다 | 같은 실수를 반복한다 | 무효 판정 이유를 문서화 |
| 결론과 한계를 섞는다 | 과장되거나 불명확한 주장이 된다 | 관찰, 해석, 한계로 분리 |

## 7. 익숙해지기 위한 연습 루틴

처음에는 아래 루틴을 매번 그대로 따라 한다.

1. 가설을 한 문장으로 쓴다.

예: "Iris role-based filtering은 FieldAgent와 Spectator가 받는 detail actor 수를 줄이고, heavy 조건에서는 outgoing bandwidth도 줄일 것이다."

2. 비교 조건을 표로 쓴다.

Generic과 Iris에서 같아야 하는 값과 달라야 하는 값을 분리한다.

3. 실행 전에 기대값을 쓴다.

예: Generic FieldAgent는 120개, Iris FieldAgent는 40개를 받아야 한다.

4. 실행 후 원본 산출물 존재를 확인한다.

`run.json`, `client_snapshots.csv`, `server_network_metrics.csv`가 모두 있는지 본다.

5. 유효성 판정을 먼저 한다.

조건이 틀리면 결과 표에 넣지 않는다. 필요하면 무효 run 표에만 남긴다.

6. 같은 window로 집계한다.

sample count, start/end time, delta 계산 방식을 같이 남긴다.

7. 관찰, 해석, 한계를 따로 쓴다.

이 단계까지 해야 "수치를 본 것"이 아니라 "실험을 한 것"이 된다.

## 8. IrisDemo에서 계속 지켜야 할 기준

Scenario A 이후에도 같은 원칙을 유지한다.

- UObject subobject replication 비교에서도 actor 수, object 수, update 빈도, client 수를 고정한다.
- seamless travel 검증에서도 travel 전후 보존되어야 하는 상태와 재생성되어도 되는 상태를 먼저 정의한다.
- 성능 비교에서는 Generic/Iris, filtering on/off, prioritization on/off 같은 변수를 한 번에 여러 개 바꾸지 않는다.
- 모든 run은 RunId 기준으로 원본 산출물과 해석 문서를 연결한다.
- 결론은 항상 "이번 조건에서는"이라는 범위를 가진다.

좋은 실험 습관은 거창한 통계 지식에서 시작하지 않는다. 같은 조건을 확인하고, 원본을 남기고, 비교 가능한 window를 고르고, 결론의 범위를 정확히 쓰는 작은 반복에서 시작한다. 이 기본기가 쌓이면 Unreal Insights, NetTrace, 더 복잡한 replication 지표도 훨씬 덜 막연해진다.
